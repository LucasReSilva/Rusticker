# sticker-export Specification

## Purpose
Turn the stickers detected in the user's image into WhatsApp-ready sticker packs (size-limited transparent WEBP stickers, a tray icon, valid pack sizes, locale-neutral archives) entirely inside the browser, and keep the user informed while doing it.

## Requirements

### Requirement: Sticker image format
Each exported sticker SHALL be a WEBP image of exactly 512x512 pixels that preserves the sticker's transparent background. The exported image MUST be produced from the 512x512 sticker returned by detection without cropping, rescaling, or flattening transparency.

#### Scenario: Transparent 512x512 WEBP
- **WHEN** a sticker is exported
- **THEN** its file is a WEBP image of 512x512 pixels
- **AND** pixels that were transparent in the detected sticker remain transparent

### Requirement: Sticker size budget
Each exported WEBP sticker SHALL be at most 100 KB (100,000 bytes). The system SHALL start from a high encoding quality and lower it automatically until the file fits, keeping the highest quality found that fits, and it MUST NOT lower the quality below a fixed minimum. If a sticker exceeds the budget even at the minimum quality, the system SHALL still export it at the minimum quality, mark it as over budget, and warn the user how many stickers exceed the budget.

#### Scenario: Sticker already fits at the starting quality
- **WHEN** a sticker encoded at the starting quality is at most 100,000 bytes
- **THEN** that encoding is used without further reduction

#### Scenario: Quality is reduced until the sticker fits
- **WHEN** a sticker encoded at the starting quality is larger than 100,000 bytes but fits at some quality at or above the minimum
- **THEN** the exported file is at most 100,000 bytes
- **AND** it uses the highest quality the search found that fits

#### Scenario: Sticker cannot fit even at the minimum quality
- **WHEN** a sticker encoded at the minimum quality is still larger than 100,000 bytes
- **THEN** the sticker is exported at the minimum quality and marked as over budget
- **AND** after the export the user sees a localized warning stating how many stickers exceed the budget

### Requirement: Encoded size reporting
The system SHALL compute each sticker's final encoded WEBP size in the background after detection, without requiring the user to export, and SHALL expose it per sticker so the interface can show it in kilobytes formatted for the active locale. Until a sticker's size is known it SHALL be reported as pending. Over-budget stickers SHALL be distinguishable from stickers within budget. The export SHALL reuse these encodings rather than encoding the same sticker twice.

#### Scenario: Size becomes available after detection
- **WHEN** detection produces stickers and background encoding of a sticker finishes
- **THEN** that sticker's encoded size in bytes is available to the interface

#### Scenario: Size is pending
- **WHEN** a sticker's encoding has not finished yet
- **THEN** its size is reported as pending rather than as zero

#### Scenario: New detection invalidates sizes
- **WHEN** detection runs again and produces a new set of stickers
- **THEN** sizes from the previous set are not reported for the new stickers

### Requirement: Tray icon
Every exported pack SHALL include a tray icon: a 96x96 PNG with a transparent background, generated by scaling down the sticker the user chose as tray icon. When the user has not chosen a sticker, or the chosen sticker no longer exists, the system SHALL use the first sticker in detection order. All packs of the same export SHALL use the same tray icon.

#### Scenario: User-chosen tray icon
- **WHEN** the user marked a sticker as tray icon and exports
- **THEN** each pack contains a 96x96 transparent PNG tray icon generated from that sticker

#### Scenario: No tray icon chosen
- **WHEN** the user exports without choosing a tray icon
- **THEN** the tray icon is generated from the first sticker in detection order

#### Scenario: Chosen sticker was removed
- **WHEN** the sticker chosen as tray icon was removed before exporting
- **THEN** the tray icon is generated from the first remaining sticker in detection order

### Requirement: Pack size and splitting
A pack SHALL contain between 3 and 30 stickers. With 3 to 30 stickers the system SHALL produce exactly one pack. With more than 30 stickers the system SHALL produce the minimum number of packs needed (the total divided by 30, rounded up) and SHALL distribute the stickers as evenly as possible, with earlier packs receiving any extra sticker, so that pack sizes differ by at most one and no pack has fewer than 3 stickers. Stickers SHALL keep detection order across and within packs. With fewer than 3 stickers the export SHALL be blocked.

#### Scenario: Fewer than 3 stickers
- **WHEN** there are 0, 1, or 2 stickers
- **THEN** no pack is produced and the export action is unavailable

#### Scenario: Single pack
- **WHEN** there are 3 stickers, or 30 stickers
- **THEN** exactly one pack is produced containing all of them

#### Scenario: 31 stickers
- **WHEN** there are 31 stickers
- **THEN** two packs are produced with 16 and 15 stickers, in that order

#### Scenario: 60 stickers
- **WHEN** there are 60 stickers
- **THEN** two packs of 30 stickers are produced

#### Scenario: 61 stickers
- **WHEN** there are 61 stickers
- **THEN** three packs are produced with 21, 20, and 20 stickers, in that order

#### Scenario: Order is preserved
- **WHEN** stickers are split into several packs
- **THEN** concatenating the packs in order yields the stickers in detection order

### Requirement: Pack archive layout and file names
Each pack SHALL be delivered as its own zip archive. All file names SHALL be locale-neutral and MUST NOT depend on the active language. Pack archives SHALL be named `rusticker-pack-<n>.zip` with `n` starting at 1. Inside each archive, stickers SHALL be numbered from 01 within that pack, in pack order, with two-digit zero padding: the WEBP stickers at the archive root as `sticker_<NN>.webp`, a lossless 512x512 PNG copy of each sticker as `png/sticker_<NN>.png`, and the tray icon as `tray_icon.png` at the archive root. The archive SHALL contain no other files.

#### Scenario: Single pack contents
- **WHEN** 17 stickers are exported
- **THEN** one archive named `rusticker-pack-1.zip` is produced
- **AND** it contains `sticker_01.webp` through `sticker_17.webp`, `png/sticker_01.png` through `png/sticker_17.png`, and `tray_icon.png`, and nothing else

#### Scenario: Numbering restarts per pack
- **WHEN** 31 stickers are exported
- **THEN** `rusticker-pack-1.zip` contains `sticker_01.webp` through `sticker_16.webp`
- **AND** `rusticker-pack-2.zip` contains `sticker_01.webp` through `sticker_15.webp`, where its `sticker_01.webp` is the 17th sticker in detection order

#### Scenario: Names do not depend on locale
- **WHEN** the same stickers are exported with the interface in pt-BR, en, and es
- **THEN** the archive and file names are identical in all three cases

### Requirement: Downloading packs
Exporting SHALL deliver the pack archives to the user as downloads generated locally in the browser. With one pack, the primary action SHALL download that single archive. With several packs, the primary action SHALL download every pack archive in order, and the interface SHALL also offer a separate action per pack so any pack can be downloaded again individually.

#### Scenario: One pack
- **WHEN** the user triggers the primary export action with 3 to 30 stickers
- **THEN** exactly one archive, `rusticker-pack-1.zip`, is downloaded

#### Scenario: Several packs
- **WHEN** the user triggers the primary export action with more than 30 stickers
- **THEN** each pack archive is downloaded, in pack order
- **AND** a per-pack download action is available for each pack

### Requirement: Export feedback
The export interface SHALL keep the user informed, with all user-visible text, including accessible labels, present in every supported locale and using locale-aware parameters and plural forms:
- The primary export action SHALL be disabled while there are fewer than 3 stickers (with a visible explanation of the minimum), while detection is running, and while an export is in progress.
- When the stickers will be split into several packs, the interface SHALL show an informational notice with the sticker count and the number of packs before the user exports.
- While exporting, the interface SHALL show progress.
- When an export finishes, the interface SHALL show a success notification with the number of stickers and packs; for several packs, the per-pack actions SHALL identify each pack as "pack n of total".
- Over-budget stickers SHALL produce a warning (see Sticker size budget); an export failure SHALL produce an error notification and leave the interface usable for a retry.

#### Scenario: Too few stickers
- **WHEN** fewer than 3 stickers are present
- **THEN** the primary export action is disabled and a localized explanation of the 3-sticker minimum is visible

#### Scenario: Split notice
- **WHEN** 31 or more stickers are present
- **THEN** a localized informational notice states the sticker count and the number of packs they will be split into

#### Scenario: Progress and disabled while exporting
- **WHEN** the user starts an export
- **THEN** progress is shown and the primary action is disabled until the export ends

#### Scenario: Success notification
- **WHEN** an export of 17 stickers in one pack completes
- **THEN** a localized success notification reports 17 stickers in 1 pack, using the correct plural forms for the active locale

#### Scenario: Failure is recoverable
- **WHEN** encoding or archiving fails
- **THEN** a localized error notification is shown and the primary action becomes enabled again

#### Scenario: Browser cannot encode WEBP
- **WHEN** the browser cannot produce WEBP images
- **THEN** no archive is downloaded and a localized error explains that this browser cannot create WhatsApp stickers

#### Scenario: Text exists in every locale
- **WHEN** the interface is shown in pt-BR, en, or es
- **THEN** every export label, notice, progress text, and notification has a translation in that locale

### Requirement: Export stays on the device
Encoding, tray-icon generation, and archive creation SHALL happen entirely on the user's device. Exporting MUST NOT send sticker images, archives, or any data derived from them over the network.

#### Scenario: No network traffic during export
- **WHEN** the user exports packs with network access disabled
- **THEN** the export completes and the archives are downloaded

### Requirement: Static Telegram sticker-file export

The application SHALL let the user export the current selection of stickers as static PNG or WEBP image files for a user-controlled Telegram import workflow. Each image SHALL preserve transparency and have one dimension exactly 512 pixels and the other dimension no greater than 512 pixels. Export names SHALL be locale-neutral. A ZIP archive MAY group the files, but it SHALL be described only as a collection of static sticker files and SHALL NOT be presented as a native Telegram sticker set or as directly importable by Telegram. The application SHALL provide localized instructions to continue with Telegram's editor or `@Stickers`. Encoding and archive creation SHALL happen locally, and the application SHALL NOT upload images or call Telegram APIs.

#### Scenario: Export transparent PNG files

- **WHEN** the user selects PNG and exports one or more stickers
- **THEN** each output is a transparent PNG with one dimension exactly 512 pixels and the other at most 512 pixels
- **AND** the files use stable, locale-neutral names

#### Scenario: Export transparent WEBP files

- **WHEN** the user selects WEBP and the browser supports WEBP encoding
- **THEN** each output is a transparent WEBP with one dimension exactly 512 pixels and the other at most 512 pixels

#### Scenario: Explain the Telegram handoff

- **WHEN** the Telegram export controls are shown
- **THEN** localized instructions explain that the user must continue in Telegram's editor or with `@Stickers`
- **AND** the ZIP is identified as static image files rather than a native Telegram sticker set

#### Scenario: Keep Telegram processing local

- **WHEN** the user creates a Telegram sticker-file export
- **THEN** encoding and archive creation occur on-device without Telegram API calls or image uploads

#### Scenario: Empty selection

- **WHEN** no stickers are selected
- **THEN** the export action is unavailable

#### Scenario: Export the current batch selection

- **WHEN** the Telegram export controls are shown in the editor
- **THEN** the exporter receives the current combined batch sticker selection
