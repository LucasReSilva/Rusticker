Run [build-fixture.ps1](build-fixture.ps1) using the command in the [README](README.md).
It requires Windows PowerShell, System.Drawing, and FFmpeg with the `libwebp`
encoder on PATH. It reads no user images and makes no network requests. All
pixels are solid geometric shapes generated by the script. Only the script and
this record belong in Git; `generated/` is ignored.

## Procedure when a device is available

1. Generate the fixture locally. Record the generator output/hash and exact OS,
   Sticker Maker version name/build, and WhatsApp version. Obtain the importer
   through its official store listing linked in the design; do not substitute an
   unverified APK download. Do not use personal images or existing sticker packs.
2. Transfer only `metadata-probe.wastickers` to the test device. Open/share it
   from a file manager to Sticker Maker. Record the file manager, routing method,
   and MIME type if observable; record failure if the app is not offered.
3. Observe the imported pack title and publisher/author. Record the exact values
   shown and where they appear. Require `Rusticker Metadata Probe` and
   `Rusticker Synthetic Fixture`, not default values or the archive filename.
4. Repeat with the byte-identical `.zip` file and record the result separately.
   Extension-based routing and content acceptance are distinct observations.
   If either archive is rejected, record the error and investigate the accepted
   structure before changing a candidate cover name or layout. Record every
   variation explicitly rather than silently replacing the baseline.
5. If import succeeds, add the synthetic pack to WhatsApp and verify all three
   stickers and the displayed pack metadata. Record success/failure separately
   from Sticker Maker's preview. Do not send stickers to another person or group.
6. Add the observed exact build, extension, layout, metadata values, and handoff
   result to this record as text. Keep device screenshots, images, archives, and
   account data local. Use the evidence to decide task 4; modify the product
   specification only if the required stable importer contract is demonstrated.

A failed run is evidence for the tested build and fixture, not a blanket no-go
for every importer. A successful run is likewise limited to the named build and
platform; it does not establish iOS or cross-version compatibility.
